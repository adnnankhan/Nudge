01 · Idea

Open the prototype (opens in a new tab)

Case study · 2026

Never miss what your coding agent needs.

Nudge is a phone app for people who run AI coding agents — Claude Code, Codex and Cursor. When an agent stops to ask, Nudge brings it to your phone, explains it in plain words and lets you answer safely, wherever you are. Each agent’s own app shows only that agent; Nudge puts them all in one place — and makes every request safe to answer, not just quick.

02 · Key screens

03 · Problem statement

  1. 01

    Work stops

    The agent waits until the person comes back.

  2. 02

    The session can drop

    On Windows laptops, the computer goes to sleep and the connection is lost.

  3. 03

    Rushed decisions

    Faced with a pile of waiting prompts, people approve without reading and answer half-way. The agent builds the wrong thing, work is redone, and time and usage limits are wasted.

  4. 04

    Juggling agents

    People running more than one agent have no single place to see which one is waiting.

The agent doesn’t fail. It waits — and nobody’s there to answer.

People who run AI coding agents, from professional developers to non-coders, step away while the agent works — a short break, a class or meeting, an overnight run. While they’re away, the agent stops to ask for permission or a question, and they don’t see it.

How might we make sure people never miss what their coding agents need, and can answer correctly and safely from wherever they are?

04 · Research

Before designing anything, I checked two things: can this be built, and is the problem real?

A great design for an impossible or imaginary product is wasted work.

Can it be built?

  • A helper on the computer, a relay and the phone app — a phone can’t reach a laptop directly on most networks; a relay passes messages in both directions without the user setting anything up.
  • End-to-end encryption with QR pairing — a phone that can approve commands is a remote control for someone’s computer, so the relay only carries locked messages it can’t read.
  • Cost checked before committing — the relay can start on a free tier, so the idea doesn’t depend on a big server bill. The real fixed costs are the app store accounts.
  • Each agent shows only what it supports — Claude Code and Codex allow approvals, questions and control; Cursor allows approvals only. A button that can’t work is worse than no button.
  • Undo restores files only — commands an agent already ran (installs, deletes) can’t be reversed. Saying so up front avoids false confidence.
  • Every technical constraint listed with its real-world solution before drawing a screen — each one is a design decision in disguise: what the user sees when the phone is offline, the computer sleeps or a request times out.

I didn’t want to design for a problem I’d only imagined, so I tested the idea against facts first.

  • Facts only — so I wouldn’t build on a hunch.
  • Facts and hypotheses in separate columns — so my assumptions couldn’t pass as evidence.
  • Only the features the facts support — so every feature in Nudge traces back to a real problem.
  • Official apps already handle basic approvals — so a plain “approve from your phone” app wouldn’t be enough; Nudge had to solve what’s still missing.

What people told me

  • I talked to 10–12 people who use coding agents before building on the facts — online posts show what’s loud, not always what’s common. They face this problem, and said an app like this would help them.

05 · Concept thinking

I didn’t want just a way to say yes. I wanted a remote for all your agents.

One hub that shows what’s working, what’s waiting and what’s done — because people running agents need the whole picture, not one prompt at a time.

  • Built on the gaps the facts showed, not on what official apps already do — basic alerts and approvals already exist. The gaps: one place for every agent, plain-language risk, proof that an answer arrived, a computer that stays awake.
  • Every kept feature answers a fact from the research — from pairing by QR to voice replies.
  • Questioned, then kept: starting a new task from the phone — I first thought people would start tasks at their desk, but a task often finishes while you’re away, and you want to start the next step without going back.
  • Cut: editing code and separate commit/push buttons — a phone is the wrong place to write code, and commits already arrive as approvals.
  • Later: history and trust rules (“always allow this in this project”) — they need real usage before they can be designed well.

06 · User flow

I mapped every path from sign-in to every feature, including what happens when things go wrong.

That’s where trust is won or lost. I made each call myself:

  • Sign-in: Google or email + password — the two most familiar options.
  • Setup starts with a short explanation — the first step happens on the computer, not the phone; people need to know why before they install anything.
  • The helper finds agents and the user confirms each one — so nothing connects without a yes.
  • Notifications asked for right after pairing, with a reason — the moment the value is obvious.
  • Keep-awake offered as soon as Home opens — so the session doesn’t drop on the first use.
  • Approve from anywhere with Face ID or fingerprint; typing needs the app open — a typed answer deserves a full screen.
  • Several requests from one session become a queue — you review them in order instead of hunting.
  • You always know what happened to your answer — so you never wonder whether a tap counted.
  • Stop confirms only when files have changed — asking every time teaches people to tap through confirmations.
  • Undo goes back one step, with “Go back further” — the common case is one tap; bigger rollbacks are a deliberate choice.
  • Cursor’s Stop button is shown with an explanation, not hidden — people understand the limit rather than wondering where the control went.
  • Every failure gets one clear message and one next step — so nothing fails silently, from a sleeping computer to a failed QR scan.
  • Taking over a session started in the terminal is part of Stop — it asks once (“This stops it in your terminal and continues from your phone”) instead of adding a separate “Take over” button.

I turned the flow into charts anyone could follow without me explaining them.

A flow only I understand can’t guide the design.

  • Neutral colours, with one colour reserved for edge cases — so the happy path reads first and the failure paths stand out.
  • Clean and precise, not sketchy — the charts became the reference for every screen that followed.

08 · Wireframes

53 mid-fidelity wireframes covered every screen in the flow before any visual design.

So structure and flow were settled before style could distract from them.

  • A floating bottom navigation, like iOS apps use today — it keeps content visible and is reachable with one thumb.
  • Four items, not three — three looked unfinished at the bottom of the screen.
  • “Add a computer” lives in the computer dropdown — that’s where people look for their computers.
  • One more check for anything missing before moving on — a missing screen costs minutes now and days after visual design.
  • Feasibility re-checked against an app built on the same idea — so the design wouldn’t promise anything impossible. It confirmed the limits (Undo restores files only, Cursor can’t be controlled) and how to handle sessions started in the terminal.

09 · Moodboard

I explored colour and type directions with Claude, and rejected most of them on purpose.

The first options were rarely good enough to build a product on.

  • Rejected the first set as dated — styles from 2020 — a tool for AI agents has to feel current.
  • Asked for a mix of two directions, held to HCI and Google guidelines, contrast and spacing — so a style choice couldn’t turn into a usability problem later.
  • Chose minimalism with modern effects and strong typography — a screen you decide on in seconds has to stay calm; Dribbble references set the quality bar.
  • Rejected directions that looked “lacking”, even when they followed the rules — correct isn’t enough; it has to feel premium.

I built the system one decision at a time, each option checked against platform guidelines.

So no visual choice could break usability later.

  • IBM Plex Sans and Plex Mono, chosen after comparing options on real screens — Mono only for commands, project names and times, so code reads as code.
  • Colour left until last — so it couldn’t hide weak layout or hierarchy.
  • Soft, rounded shapes on an 8-point grid with 16px side margins; 44 × 44 pt touch targets — spacing stays consistent, and Apple’s minimum means every tap lands.
  • Glass only on buttons and floating bars, never as decoration — the tab bar gets stronger blur, so content behind it turns to haze instead of fighting the labels.
  • Colour means risk or status — nothing else — one glance tells you how careful to be. Status is never colour alone: always an icon and a word, so it works for colour-blind people too.
  • Answers always in the same order: numbered options, typed answer last — so every question works the same way.
  • Text sizes follow Apple’s type ramp, nothing below 12px except Apple’s own 10px tab labels — text stays legible and the app feels native.

  • App icon (light tile)

The first full design got a hard review, and most of the changes came from removing things.

Every extra element competes with the one decision on screen.

  • Home order kept: Needs you → Working → Completed — what needs you must always come first.
  • Settings moved to the top-right; New task to the centre of the tab bar — where the most-used action belongs.
  • No countdown rings or timer pills — a ticking clock pushes people to approve without reading, the exact problem Nudge exists to fix. Requests show “x min ago” and “Goes back to your computer after 10 min” instead.
  • Friction matches risk — a dangerous command deserves a deliberate action; a safe one shouldn’t slow you down. Low and medium: tap Approve, then Face ID or fingerprint. High: Review on Home, then Hold to approve.
  • Alerts colour only the icon, never the text — warnings stay readable and the screen stays calm.
  • Summary boxes are black and white with icons — colour is reserved for risk.
  • Rejected a grey background — it made the whole app look unfinished.
  • Named it Nudge, with a logo of rings opening outward — a signal reaching you. Blue was tried as an accent and dropped for black and white, which leaves colour free to mean risk.
  • Dark mode became the main mode, with every component built in both dark and light — it’s the version I refined furthest in Figma, and either mode stays consistent.

13 · Feedback and iteration

I put the prototype in front of a few people who use Claude Code and other agents every day.

They’re the ones who can tell what’s missing. In short: a chat-based way to work with the agent was missing, and adding a new task felt complicated.

I added chat without turning Nudge into a chat app.

Its job is still to get you the right decision fast.

  • Chat appears in only three places, so Home stays the approval hub — a card on Home opens its task’s chat · New task is “pick an agent”, then a chat · a Tasks tab lists every task from every agent.
  • The chat follows patterns people know from Claude and ChatGPT (Jakob’s Law) — nothing new to learn: your messages on the right, the agent’s as plain text, tool activity as one collapsible line, the same rounded message box.
  • New task lost its form — filling fields was exactly the friction people described. Your last project and computer are used automatically, shown as one line you can tap to change.
  • “Ask me” replaces showing everything — the agent comes to you only when you want it to: before every action, only before commands, or just when it’s done.
  • Then I walked the flows as a frustrated user and removed everything that asked twice — every repeated question is a moment someone gives up. New task remembers your choices · cards in a chat don’t repeat who and where · voice drops straight into the message box · an open app shows one banner, not a notification too · Home keeps your place · low-risk requests can be approved together with one Face ID or fingerprint check · one check covers low and medium approvals for 5 minutes; high risk always asks.
